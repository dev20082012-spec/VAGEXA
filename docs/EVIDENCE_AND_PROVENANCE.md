# Evidence and provenance

An investigative product is only as defensible as its sources. VAGEXA stores
the source, the transformation, and the person or method that produced each
layer of the case. It prefers a gap over a fluent story.

[ADR 0006](decisions/0006-evidence-and-assertion-kinds.md) is the decision form
of this policy.

## Classifications

| Classification | Meaning | Example |
| --- | --- | --- |
| `official` | Supplied under an authorised operational process. | A statement file an investigator is entitled to load into an operational deployment. |
| `public_intelligence` | Retrieved from a source that publishes the data. | A DNS answer or a public certificate log entry. |
| `synthetic` | Generated by this project for demonstration or tests. | Scenario `ring-01`. |
| `derived` | Computed from other records by a named method. | A FIFO flow, an indicator, a graph component id. |
| `unverified` | Supplied without a source the system can stand behind. | A handwritten note of an IP with no collection record. |

Classification is not a confidence percentage. A synthetic row can be internally
consistent and still be synthetic. A derived row can be reproducible and still
be an inference.

The deployment mode in [Database design](DATABASE_DESIGN.md) refuses to store
`official` and `synthetic` primary records in the same database mode. Inside a
legal case, rows are one classification for the case itself. Derived rows cite
that case. Public and unverified observations can be attached and remain
labelled. They do not wash the case into "official" certainty.

No import path strips classification. A CSV column `data_classification` is
required on synthetic bundles. Operational uploads are stamped `official` by
the use case because the deployment is in operational mode, not because the
file claimed it.

## Assertion kinds

| Kind | Use it when | Do not use it when |
| --- | --- | --- |
| `verified` | A cited field in a stored source states the claim. Example: the statement's counterparty account column contains this number. | You mean "we are sure", "the model agrees", or "a court would agree". |
| `inferred` | A named algorithm produced the claim from verified inputs. Example: FIFO moved this lot onward. | You lack the method version or the input ids. |
| `hypothesis` | A weak signal is worth a person's review. Example: holder names are similar. | You want the graph to look connected. |

These three values are the closed set. Adding a fourth requires an ADR.

User-facing text expands `verified` on first use in a report: "shown in a
source record". The word remains in the data model so the distinction the
investigators asked for stays stable.

## Provenance record

Every source file, transaction, observation, and external lookup has a
`provenance_records` row:

- classification;
- source system, such as `upload`, `dns_query`, or `synthetic_generator`;
- source reference, such as a file hash and line number, or a generator scenario key;
- collected at;
- collected by, a user id or a service name;
- method name;
- raw hash when bytes or a response body were retained.

Derived products point at an `analytical_runs` row, which holds method version,
parameters, and input hash. They also have evidence rows of kind
`analytical_finding`.

## Immutability

Source transactions, observations, provenance, evidence, findings, trace flows,
indicator rows, copilot queries, and audit events are insert-only. Database
triggers reject update and delete. A correction inserts a new evidence record
with `supersedes_id` set to the earlier one. Reports default to the newest
record in a supersession chain and can list the chain.

Relationship status is workflow. The only permitted update is the decision
fields, and the decision is also an audit event. The underlying account or
observation is not edited to match the decision.

Parser mistakes are corrected by a reprocess that inserts a new statement
pointing at the previous one, with new transaction rows. Analytical queries
read the latest statement in that chain. The previous rows stay stored. They
are not corrected by updating the amount in place. An amount that can change
without a new hash is not evidence. ADR 0012.

## Hashes

- Source file: SHA-256 of the bytes, stored on `source_files` and in provenance.
- Analytical input: SHA-256 of the canonical JSON of the seed ids, statement ids, and policy parameters.
- Analytical output: SHA-256 of the canonical JSON of the published flows or findings.
- Copilot bundle: SHA-256 of the tool payload that narration was allowed to see.

Canonical JSON means sorted keys, UTF-8, and decimal amounts as strings. The
hash function is SHA-256. The first release does not claim a notarised
timestamp or a public ledger. It claims tamper-evidence against ordinary
application writes, which the triggers and the hashes support. A database
superuser can still rewrite storage. Operational deployment therefore separates
roles and backups, as a Phase 4 requirement, before official data is trusted to
the system.

## Audit

The audit trail answers who did what to which case, with which request id, and
whether the action succeeded or was denied. It is not a second copy of the
narrative. The first action list is in [Database design](DATABASE_DESIGN.md).

Denied authorisation is audited as `denied` without reflecting the protected
narrative back to the caller beyond a generic error.

## Reports

An HTML report is itself an evidence object: bytes hashed, provenance recorded,
`report.export` audited.

The report contains, in this order:

1. Case reference, classification, and a synthetic banner when applicable.
2. Who exported it and when.
3. Source files with hashes and parser versions.
4. Seed transactions.
5. Policy name, version, and parameters.
6. Flows by layer, each with assertion kind and source transaction id.
7. Residuals and unresolved counterparties.
8. Indicators with thresholds and support ids.
9. Infrastructure observations with times.
10. Relationships split into confirmed, proposed, and rejected.
11. A limitations section. The export fails server-side if that section would be empty.
12. The sentence: indicators and attributed paths are investigative aids and are not determinations of guilt.

The report does not embed a score of culpability. It does not include data from
cases the exporter cannot open.

## Reproducibility

A finding is reproducible when the method version, the parameters, and the
input hash are stored and the code for that version still runs. Tests in the
repository pin `fifo.v1` and `indicators.v1`. When a method changes, the version
changes. Old runs keep their old version in the row so a later code change does
not pretend to be what the investigator ran.

## Synthetic data

Synthetic records exist to test and to demonstrate. They are generated from a
scenario file with a known ground-truth file. The generator writes:

- statement CSVs;
- complaint JSON;
- infrastructure observation JSON;
- `ground_truth.json` for tests only;
- a batch id stamped on every synthetic row.

Ground truth lists planted transfers, the shared beneficiary, the shared
domain, and the noise transactions that must not become `verified` links.
Investigators in a demo can see the synthetic banner. They are not shown the
ground-truth file inside the case UI. Tests read it from the fixture path.

Mixing a synthetic batch into an operational case is a failed request, not a
warning. Promoting a synthetic case to official by updating the column is
blocked by the classification check and by the absence of an update path on the
evidence that was generated from it.

## Minimum contents before a demo is shown to anyone external

- the data-mode banner;
- method versions on the trace they are looking at;
- at least one visible residual or gap, so the demo does not imply perfect coverage;
- the licence and ownership placeholder still visible in the repository, so a
  demo is not mistaken for a released government system.
